## Summary

The service is in very good shape for its size. Every staticcheck check passes, style included,
on all three modules. Statement coverage is 93.1% across the module. gosec, govulncheck and
fuzzing run on every change, the service has no third-party dependencies, and everything it runs
is pinned. Where the code is described elsewhere (the spec, the logs, the settings, the
architecture), a test fails when the two disagree. No finding was critical, and none put a
running deployment at risk.

The gaps were at the edges: files a project others copy needs, checks that stopped short of the
scripts, the workflows and coverage, build inputs that could change without anyone deciding, a
few stale documents, and above all how much work it takes to start a new service from it.

| Area | Rating | In short |
| ---- | ------ | -------- |
| Code quality | Strong | Every staticcheck check passes; idiomatic, small packages; errors, contexts and goroutines handled carefully. 39 idioms a newer Go says more simply. |
| Architecture | Strong | Clear package roles and import rules, enforced by a test; 44 decision records. |
| Testing | Strong | 93.1% coverage, the race detector always on, contract, spec, fuzz, integration, load and soak tests. Coverage wasn't measured in CI. |
| Security and supply chain | Strong | Hashed keys, authentication by default, bounded input, distroless non-root image, every action and image pinned. No license or security policy. |
| Observability | Strong | A checked log contract, request and runtime metrics, W3C trace context; no spans yet. |
| Operations | Strong | Fail-fast configuration, deadlines, graceful shutdown that answers what's in flight, memory limit from the container. |
| CI and releases | Good | Least-privilege, pinned, timed-out jobs; release images smoke-tested by digest. Scripts, workflows and module tidiness unchecked; the runner image unpinned. |
| Documentation | Good | Thorough guides with drift tests; a few passages no test covers had gone stale. No written standards. |
| Developer experience | Good | One `make` target per task, nothing to install but Go, Docker and `make`; running anything needs Docker. |
| Starter template | Gaps | Starting a service means renaming 230 places by hand and copying about 3,000 lines for a new resource. |

## Strengths

- **Static analysis is clean, all of it.** Every staticcheck check passes on all three modules,
  doc comments and naming included, which is rare.
- **The production code avoids the usual traps.** No `init` functions, no `os.Exit` outside
  `main`, no package-level mutable state (only shared, never-modified values), no
  `http.DefaultClient` but in the healthcheck probe (bounded by its own 2-second timeout), no
  `panic` but a deliberate abort, and `context.Background()` only in the two server-level log
  lines that can't belong to a request.
- **Descriptions are held to the code.** The spec runs against the real handlers for every
  documented status; the log contract against every line the service writes; the settings,
  stubs, dashboards, load-test mix, configurations, package imports and decision records each
  against the code. A change that forgets one fails, naming it.
- **Every request is bounded and answered.** A deadline inside the write timeout, body and header
  limits, an in-flight cap, per-client rates with a bounded memory, JSON errors with codes for
  every request (unknown routes included), and shutdown that answers what's in flight.
- **The supply chain is tight.** No dependencies in the service, tools at pinned versions or
  digests, actions at SHAs, Dependabot on all of them, SBOM and provenance on release images,
  and images smoke-tested on both platforms, by digest, before they're tagged.
- **Changes are cheap to make safely.** A change file and a decision record each, so pull
  requests don't conflict; breaking API changes flagged by a tool; known configurations held to
  starting.

**A-6** is high for a template in particular: without a license, nobody else may legally copy or
adapt the code, which is a template's whole purpose.

**A-12 and A-13.** The drift tests cover what the code describes in structured form; what they
can't parse, prose, drifts. The fix is to describe less in prose that a test can't check, and
link to what one can: the README's layout now links to the package table in the architecture,
which `docs/architecture_test.go` keeps exact.

**A-14.** `TestLogRejected` waits out the server's 5-second read-header timeout, which isn't
configurable; making it an option of `httpx.Serve` would let the test use 100 milliseconds.
Where `TestRunWithAPIKeys` spends its 5 seconds wasn't established.

## As a starter for new services

The template's purpose is for a team to start a new Go service from it and have a first real
endpoint serving quickly. Today:

- **Renaming it** means changing `golang-vibe-starter` in about 230 places across 105 files: the
  module path in every import, the image and compose names, and the docs.
- **A new resource** means copying `internal/item`, about 3,100 lines with its tests, of which
  much is plumbing every resource repeats (conditional requests, paging, error mapping), and then
  changing six more places a new route touches: the spec, `docs/curl.md`, the WireMock stubs, the
  load test's traffic mix, an integration feature, and `cmd/api`'s wiring. The drift tests catch
  all but the integration feature when one is missed, which makes it safe, but not fast.
- **Running it at all** needs Docker: the only store is the upstream, so `UPSTREAM_URL` is
  required, and the in-memory store exists only for tests.
- **Most microservices need dependencies** the service may not have (A-16).

The [roadmap](../ROADMAP.md) proposes, in order: shared building blocks for resources in `httpx`;
a run mode with no infrastructure; `make init` to rename and reset it, tested on a copy; a
resource generator whose output passes every check as generated, tested the same way; and an ADR
allowing vetted dependencies in adapter packages only, which a SQL store, OpenTelemetry spans and
events with a worker would build on. Then, as services multiply: a platform module, a Kubernetes
deployment checked in CI, per-service dashboards and alerts, a typed client, and a spec per
resource.

## Still open

- **A-14**, the two slow tests.
- **deadcode isn't in `make lint`.** Of its five findings, `item.Restore` and `item.NewCursor`
  are API for store implementations (the test store uses them) and `logx.RequestID` is for
  handlers; using it would need a way to mark such API as wanted.
- **Proposals declined for now**, on the roadmap for later: a circuit breaker, bulkheads and the
  other resilience items; image scanning and signing.

The standards, the lint target and the coverage floor are what keep these findings from
returning. A review like this one is worth repeating before version 1.0, and when the template
grows a second service.
